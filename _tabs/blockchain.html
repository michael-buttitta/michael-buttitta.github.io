01 The problem

The trust problem

Imagine ten companies that trade with each other all day and need one shared record of who owes what. Who owns that record? Who is allowed to update it? And when two copies disagree — whose version is the truth? Every multi-party system ever built has had to answer these questions somehow.

Run a trading day below. When every company keeps its own books, small differences creep in — a missed entry here, a typo there — and reconciling them costs real time and money. The classic fix is to appoint one trusted bookkeeper. That works, and it is how most of the world runs today. But now everyone depends on one organization’s honesty, competence, and uptime.

Blockchain was invented to explore a third answer: can many independent computers maintain one shared source of truth, with no single keeper? The rest of this page unpacks how that works — and, just as important, what it costs. Neither model is simply “better.” They are different trade-offs, and by the end you should be able to tell which one a given problem deserves.

02 Two architectures

Centralized vs decentralized systems

A centralized system has one database, one owner, one administrator — a single point of control. A decentralized system has many nodes, a shared ledger, and a consensus rule instead of a boss. Toggle between them below, then try knocking a machine offline in each world.

Requests failed–
System status–

Centralized

One database → one owner → one administrator → single point of control.

Examples: a bank’s core ledger, a company ERP, Google Docs, Amazon’s inventory database.

Strengths

  • Fast — one machine (or cluster) decides, no waiting for votes
  • Cheap — data is stored once, not replicated to strangers
  • Simple — decades of mature tooling and expertise
  • Easy governance — one owner can fix mistakes and upgrade schemas
  • High throughput — tens of thousands of writes per second is routine

Weaknesses

  • Single point of failure — if it goes down, everything stops
  • Requires trust in the operator’s honesty and competence
  • The owner can censor, block, or reverse transactions
  • Insiders can quietly alter records
  • An outage or breach affects every user at once

Decentralized

Many nodes → shared ledger → consensus → replication.

Examples: Bitcoin, Ethereum, Hyperledger Fabric, and (conceptually) content-addressed systems like IPFS.

Strengths

  • Fault tolerant — losing nodes barely dents the network
  • Transparent — every participant can verify the full history
  • Tamper resistant — rewriting history requires beating the whole network
  • No single owner — no one party can unilaterally change the rules

Trade-offs

  • Slower — every write waits for network-wide agreement
  • More expensive — every node stores and verifies everything
  • Harder governance — upgrades need broad coordination
  • Replication overhead grows with every participant
  • Consensus is eventual — brief disagreement windows are normal

Keep this pairing in mind for the whole page: decentralization buys resilience and neutrality by spending speed, cost, and simplicity. Good engineering is choosing which side of that trade a problem actually needs.

03 The data structure

What is a blockchain?

Strip away the hype and a blockchain is a surprisingly simple data structure: a list of blocks, where each block bundles some transactions and carries the cryptographic fingerprint of the block before it. That one design choice — every block pointing at its parent’s fingerprint — is where all the interesting properties come from.

Click any block to inspect what is inside. Every hash you see is a real SHA-256 digest computed in your browser, and each block’s “previous hash” field really is the hash of the block to its left — that is the link in the chain.

    Select a block above to inspect its contents.

    Transactions

    The payload: transfers, records, or events. Real systems bundle hundreds or thousands per block and summarize them with a Merkle tree — a hash of hashes that lets anyone prove a single transaction is included without downloading the whole block.

    Timestamp

    When the block was produced. Nodes tolerate small clock drift, so blockchain time is approximate — good enough for ordering blocks, not for stopwatches.

    Previous hash

    The fingerprint of the parent block. This is the “chain”: change any historical block and every descendant’s link breaks, as you will see two chapters from now.

    Nonce

    A number the block producer is free to vary. In proof-of-work systems, miners grind through nonces until the block’s hash satisfies a difficulty target. In other systems it plays a smaller role — here, think of it as the adjustable dial.

    Current hash

    The SHA-256 fingerprint of everything above. It is not stored in the block so much as derived from it — recompute it any time to check that nothing changed.

    Where does it live?

    On every node’s disk, in full. A ledger replicated to thousands of machines is the opposite of a normal database’s “store it once” economics — the memory & storage exhibit shows what those reads and writes actually cost.

    04 The fingerprint machine

    Hashing: fingerprints for data

    A cryptographic hash function takes any input — a word, a contract, a terabyte — and produces a short, fixed-size fingerprint. Same input, same fingerprint, every time. Change one letter and the fingerprint changes beyond recognition. Blockchains are built out of this one primitive.

    Type below. Your browser computes a real SHA-256 hash on every keystroke — the same algorithm Bitcoin uses. Watch the avalanche effect: edit a single character and see how many of the 256 output bits flip.

    Deterministic

    The same input always produces the same hash, on any machine, in any decade. That is what lets thousands of independent nodes check each other’s work.

    One-way

    Going from input to hash is fast; going from hash back to input is computationally infeasible. The only known way is guessing inputs until one matches.

    Avalanche effect

    A one-bit change to the input flips, on average, half of the output bits. Similar inputs give wildly different hashes, so you cannot “sneak up” on a target hash by tweaking.

    Integrity checking

    Publish a file’s hash and anyone can later verify the file was not altered — recompute and compare. A blockchain applies this idea to an entire ledger, block by block.

    Hashing is pure arithmetic — bit shifts, additions, and XORs executed billions of times per second. If you want to see how a processor actually churns through work like this, the Inside a Modern CPU exhibit walks through the pipeline instruction by instruction.

      Notice what “re-mining” costs even in this toy: each repaired block takes hundreds of hash attempts at our easy difficulty. On a real proof-of-work network the difficulty is astronomically higher, and here is the part that matters: while you rebuild history, the honest network keeps extending the real chain. To win, you would have to redo the work of every block after your edit and outpace everyone else combined — then convince every node to accept your version. Immutability is not a law of physics; it is an economic wall that gets taller with every block stacked on top.

      06 Agreement at scale

      Distributed consensus

      A chain of hashes proves history is internally consistent — but which history? Hundreds of independent nodes, each with its own copy of the ledger, must converge on one answer with nobody in charge. Watch a transaction ripple across the network below.

      Why every node keeps a full copy

      If you only trust your own disk, you never have to ask anyone what the ledger says. Replication is the price of removing the trusted middleman — storage is spent to buy independence.

      Validation before gossip

      Nodes do not blindly forward data. Each one checks signatures, balances, and rules first, and drops anything invalid. Bad transactions die within a hop or two.

      Forks are normal

      Two block producers can succeed at nearly the same moment, briefly splitting the network into two histories. The rule “follow the chain with the most accumulated work (or stake)” resolves it within a few blocks — which is why recent blocks are treated as tentative and older ones as settled.

      Byzantine fault tolerance

      The deep problem here is agreeing when some participants may lie or fail arbitrarily — computer science calls these Byzantine faults. Every consensus mechanism in the next chapter is a different strategy for surviving them.

      07 Four strategies

      Consensus mechanisms

      “Who gets to add the next block?” has more than one good answer. Proof of Work sells the right for energy; Proof of Stake sells it for locked-up capital; committee protocols like PBFT vote; Proof of Authority simply appoints known validators. Each optimizes for different priorities.

      There is no free lunch here: the mechanisms that are open to anyone pay for it in energy or capital lock-up and slower finality, while the fast, efficient ones quietly reintroduce a guest list. Choosing a consensus mechanism is choosing how much you trust the participants.

      08 Two deployment models

      Public vs private blockchains

      “Blockchain” covers two very different deployment models. Public chains are open networks anyone can join; private (permissioned) chains restrict participation to vetted organizations. They share the data structure but differ in almost everything else.

      Public

      Permissionless — the network is the product.

      • Anyone can run a node, transact, or produce blocks
      • No sign-up, no gatekeeper, pseudonymous participants
      • Highly decentralized; secured by economic incentives
      • Fully transparent — every transaction is world-readable
      • Governance by rough consensus of users, developers, and operators

      Examples: Bitcoin, Ethereum.

      Private / permissioned

      A shared database for organizations that half-trust each other.

      • Participants are invited, identified, and legally accountable
      • An operator or consortium controls membership
      • Modestly decentralized — typically a handful of known validators
      • Data visibility can be restricted per participant
      • Governance by contract and committee, like any joint venture

      Examples: Hyperledger Fabric, R3 Corda.

      Why do businesses usually pick the permissioned kind? Because their problem is rarely “trust no one” — it is “trust each other a little, verify a lot.” Ten banks sharing a settlement ledger already know each other’s legal names; they need shared bookkeeping with tamper evidence, privacy from competitors, regulatory compliance, and someone to call when things break. A permissioned chain (or, honestly, a well-designed shared database) fits that shape. The radical openness of a public chain solves a harder problem those firms usually do not have — and charges accordingly.

      09 Programmable ledgers

      Smart contracts

      Early blockchains recorded one thing: transfers. The next idea was to let the ledger run code. A smart contract is a program stored on the chain; when a transaction calls it, every validating node executes the same code on the same inputs and must arrive at exactly the same result — which then becomes part of the shared ledger.

      The key property is determinism. Contract code is forbidden from doing anything whose answer could differ between machines — no random numbers, no clock reads, no calling the open internet. Given the same chain state and the same transaction, node A in Tokyo and node D in São Paulo must compute byte-for-byte identical results, or consensus would shatter. (External facts, like our courier’s confirmation, must be delivered onto the chain as signed transactions — a role played by so-called oracles, and one of the genuinely hard problems in this field: the chain can verify that the courier said the package arrived, not that it actually did.)

      10 In the field

      Real-world adoption

      Where is this actually used? Honest answer: adoption is real but uneven — deep in a few niches, experimental in most others, and quietly abandoned in some. Each card below says where blockchain plausibly helps, how adoption is actually going, and when a plain database remains the better call.

      Financial services

      Stablecoin settlement, cross-border payments, tokenized funds and bonds.

      Why it may help
      Settlement in minutes across borders and time zones, without chains of correspondent banks each keeping their own books.
      Adoption
      The strongest of any sector — stablecoin transfer volume is measured in trillions of dollars per year, and major asset managers run tokenized money-market funds.
      Honest caveat
      Domestic payments in most countries already settle fast on centralized rails; the win is concentrated in cross-border and after-hours flows.

      Supply chains

      Product provenance, food traceability, anti-counterfeiting.

      Why it may help
      Many mutually distrustful parties (growers, shippers, customs, retailers) appending to one tamper-evident record.
      Adoption
      Mixed. Pilots were everywhere; several flagship projects (including IBM and Maersk’s TradeLens) shut down after failing to attract enough participants.
      Honest caveat
      The chain can prove nobody edited the record — not that the record was true when written. Garbage in, immutable garbage out.

      Healthcare

      Medical record integrity, clinical trial audit logs, credential verification.

      Why it may help
      Tamper-evident audit trails for records that many institutions touch and none should be able to silently rewrite.
      Adoption
      Early and narrow — mostly integrity anchoring and credentialing pilots, not primary storage.
      Honest caveat
      Patient data itself belongs in access-controlled databases; privacy law and practicality both argue against putting records on-chain. Hashes of records, not records.

      Digital identity

      Verifiable credentials — diplomas, licenses, attestations you hold yourself.

      Why it may help
      A neutral place to anchor issuers’ public keys and revocations, so a credential can be checked without phoning the issuer.
      Adoption
      Growing via standards (W3C Verifiable Credentials, EU digital identity work); the ledger is usually a small supporting component.
      Honest caveat
      Most of the machinery is plain public-key cryptography — several credential systems work fine with no blockchain at all.

      Government

      Land registries, document notarization, public procurement records.

      Why it may help
      Citizens can independently verify that titles and filings were not quietly altered — valuable where registry trust is weak.
      Adoption
      Scattered production use (Georgia anchors land titles; Estonia hash-chains state data); many announced projects went nowhere.
      Honest caveat
      A registry is only as good as the legal system behind it — a hash cannot evict a squatter or fix a corrupt clerk’s original entry.

      Enterprise consortia

      Shared audit trails, interbank reconciliation, trade finance networks.

      Why it may help
      Replaces N companies reconciling N private databases with one shared, append-only record every member can verify.
      Adoption
      Quietly steady in niches (trade finance, securities settlement pilots), far below the 2017-era hype.
      Honest caveat
      Consortium politics — who pays, who governs, who is liable — kills more projects than the technology does.

      Gaming & digital goods

      Player-owned items, collectibles, cross-game assets.

      Why it may help
      Items recorded on a public chain survive the studio shutting a server, and can be traded on open markets.
      Adoption
      A boom-and-bust cycle; a smaller, steadier scene remains after the 2021–22 collectibles frenzy deflated.
      Honest caveat
      The token proves ownership; the artwork and game logic usually still live on someone’s server. Most games are better served by ordinary databases.

      11 Engineering judgment

      When not to use blockchain

      This may be the most useful chapter on the page. Blockchain is not a better database — it is a different database that pays heavy costs (speed, storage, complexity, governance) to remove a trusted operator. If you have a trusted operator, you are paying those costs for nothing.

      Reach for a traditional database when…

      • One trusted owner exists — a company managing its own data needs PostgreSQL, not consensus
      • Speed matters — a single machine commits in microseconds; global consensus takes seconds to minutes
      • Cost matters — storing data once beats replicating it to every participant forever
      • Data changes often — an append-only ledger is miserable for records you update and delete all day
      • Privacy is critical — access control and encryption-at-rest are mature; a replicated ledger is deliberately hard to hide

      Concretely: your user accounts, product catalog, analytics events, internal inventory, medical records, and 99% of CRUD apps belong in SQL, a cloud database, or — if you need scale-out — a distributed database like Spanner or Cassandra, which replicate within one trust domain and are much faster for it.

      Consider a blockchain when…

      • Multiple independent organizations must write to one shared record
      • They do not fully trust each other — or a would-be middleman
      • Tamper evidence matters more than raw speed
      • Participants (or the public) benefit from verifying the history themselves
      • Removing the central operator is itself the point — for resilience, neutrality, or censorship resistance

      The test: if you deleted the word “blockchain” from the pitch, would the design still make sense? If a shared Postgres instance run by a lawyer-approved third party solves it, that is usually the answer.

      Do you need a blockchain? A 30-second triage

      Do several independent organizations need to write to the same records?
      Is there a party everyone would trust to host it (a regulator, vendor, or consortium operator)?
      Must the history be verifiable by outsiders, or provably tamper-evident?
      Are high throughput, low latency, or strict data privacy hard requirements?

      Answer the four questions to get a verdict.

      12 Clearing the fog

      Common misconceptions

      The word “blockchain” drags a decade of marketing behind it. Expand each card for the short, honest version.

      “Blockchain = Bitcoin”

      Bitcoin is one application of blockchain — the first and largest, but an application nonetheless. The underlying idea (a replicated, hash-linked ledger with consensus) also powers smart contract platforms, permissioned consortium networks, and systems with no currency at all. This site’s Understanding Bitcoin exhibit covers the famous application in depth.

      “Blockchain = cryptocurrency”

      Public chains use a native asset to pay block producers — that is the incentive engine. But permissioned chains run by known organizations often have no coin at all: validators participate because a contract says so, not because they are paid in tokens.

      “Decentralized means anonymous”

      Mostly the opposite. Public chains are radically transparent: every transaction is world-readable forever, tied to pseudonymous addresses. Link an address to a person once — through an exchange, a purchase, a mistake — and their entire history is exposed. Chain-analysis firms do exactly this for a living.

      “Immutable means impossible to change”

      Immutability is economic, not physical. Rewriting history requires redoing the work (or controlling the stake or committee) faster than the honest majority — wildly expensive on large networks, entirely feasible on small ones, several of which have suffered successful 51% attacks. And a community can deliberately fork: Ethereum rolled back the DAO hack in 2016 by collective choice.

      “Blockchain is automatically more secure”

      The ledger’s integrity is only one layer. Smart contract bugs, stolen private keys, compromised exchanges, and fraudulent data fed by oracles have cost users billions — none of which the chain itself prevents. A blockchain secures the record of what happened, not the wisdom of what happened.

      “Public blockchains are the only kind”

      Permissioned blockchains — Hyperledger Fabric, R3 Corda and kin — restrict who may read, write, and validate. They trade away open participation for speed, privacy, and accountable governance, and they are the variant most enterprises actually deploy.

      “Every business problem needs blockchain”

      Most do not. If one trusted party can run the database, a conventional database is faster, cheaper, more private, and easier to fix when something goes wrong. Blockchain earns its costs only when removing the trusted party is the actual requirement — see the previous chapter’s triage.

      13 How we got here

      A brief history of the idea

      Blockchain was not one invention but a slow assembly of parts — decades of cryptography research that clicked together in 2008. Scroll the timeline.

      1. 1976–79

        Public-key cryptography & Merkle trees

        Diffie and Hellman show strangers can share secrets in public; Ralph Merkle patents the hash tree — a way to fingerprint huge datasets so any piece can be verified against one small root hash.

        the raw ingredients
      2. 1991

        Hash-chained timestamps

        Haber and Stornetta propose linking documents into a chain of hashes so no timestamp can be back-dated without breaking every later link — a blockchain in all but name, published weekly as a hash in The New York Times.

        the chain, before the coin
      3. 1997–2004

        Proof of work

        Adam Back’s Hashcash makes senders burn CPU time to deter spam; Hal Finney builds reusable proof-of-work tokens. Costly computation becomes a currency of credibility.

        work as a signal
      4. 2008

        The Bitcoin whitepaper

        Satoshi Nakamoto combines the pieces — hash chains, Merkle trees, proof of work, peer-to-peer gossip — into the first system where strangers maintain a ledger with no authority at all. Nine pages that started an industry.

        the synthesis
      5. 2009

        The genesis block

        The Bitcoin network goes live. For the first time, the double-spending problem is solved in the wild without a bank. The Understanding Bitcoin exhibit dissects this machine bolt by bolt.

        theory becomes a network
      6. 2015

        Ethereum & smart contracts

        Vitalik Buterin’s Ethereum generalizes the ledger into a shared computer: arbitrary programs, executed identically by every node. Blockchains become platforms, not just payment rails.

        the ledger learns to run code
      7. 2015–17

        Enterprise platforms

        Hyperledger (Linux Foundation) and R3 Corda bring permissioned designs to consortia. A wave of corporate pilots follows — some land, many quietly conclude that a database would do.

        the permissioned turn
      8. 2020

        DeFi

        Lending, trading, and market-making rebuilt as composable smart contracts. Billions flow in — demonstrating both the power of programmable settlement and the cost of buggy code, as exploits drain protocols.

        finance as software
      9. 2021

        NFTs

        Unique on-chain tokens make digital collectibles tradable at scale — one application among many, briefly mistaken for the whole point. The speculative wave crests and recedes; the primitive (a ledger entry proving ownership of a unique item) remains.

        one application, loudly
      10. 2023–now

        Tokenized real-world assets

        Money-market funds, treasuries, and bank deposits appear on-chain from household-name institutions; stablecoins settle trillions yearly. Quieter than past cycles — and more consequential: the technology fades into infrastructure.

        boring on purpose
