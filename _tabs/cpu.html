01 The problem

Why CPUs exist

Software is just text until something runs it. A computer needs one component whose whole job is to take a program, break it into steps a machine can perform, and perform them — relentlessly, billions of times per second. That component is the CPU.

Your program

score = score + 10

One line, written for humans

Instructions

load  r1, score add   r1, r1, 10 store score, r1

Three steps, written for machines

The CPU

Executes 0 / 3 instructions

The result

score 2500

Memory updated, pixels follow

The instruction set shown here is simplified for readability — real machine instructions are raw bytes, and chapter 04 shows the real thing. The idea is exact, though: every program, from a calculator to a game engine, becomes a stream of tiny steps like these.

“The brain” — and what that metaphor hides

The CPU is often called the brain of the computer because every decision passes through it. But unlike a brain, it stores almost nothing. Your running programs live in RAM; your files live on the SSD. The CPU is pure verb — it fetches, computes, and writes back, and it is only as fast as the memory that feeds it.

Three separate physical components. When people say a computer “thinks,” they mean this trio passing data back and forth — and most of this page is about what happens inside the leftmost box.

03 The heartbeat

Fetch, decode, execute

Strip away every optimization and a CPU does exactly one thing, forever: fetch the next instruction, figure out what it means, do it, record the result. Follow one real instruction — add rax, rbx — through the whole journey.

1 · Asleep in RAM

A program is just bytes in memory. At address 0x4000 sit three of them — 48 01 D8 — which mean add rax, rbx. Nothing happens until the core asks for them.

Instructions completed: 0

A modern core does not walk this path one instruction at a time — it keeps hundreds of instructions at different points along it simultaneously. That trick is called pipelining, and it gets its own chapter below.

04 The translation

From code to machine code

A CPU cannot run Python, C, or JavaScript. It runs exactly one language: its instruction set, encoded as raw bytes. Everything you write is translated down to that — ahead of time by a compiler, or on the fly by an interpreter and JIT. Here is a real translation, byte for byte.

Every byte above is genuine: compile that function with a C compiler at -O1 on Linux and you will get these five bytes (arguments arrive in edi and esi, results leave in eax — that contract is the calling convention). There is no smaller step left: 89 F8 is the program, and the decoder reads it the way you read words.

One idea, two dialects: x86 and ARM

x86-64 CISC heritage

  • Instructions are 1–15 bytes long — compact but hard to decode
  • Rich, complex operations; ~40 years of backward compatibility
  • Runs most desktops, laptops, and servers (Intel, AMD)

ARM (AArch64) RISC heritage

  • Every instruction is exactly 4 bytes — simple, parallel decode
  • Simpler operations; the compiler strings them together
  • Runs phones, Apple Silicon Macs, and a growing share of servers

The dialects differ; the machine underneath barely does. Both families decode their instructions into internal micro-ops and execute them on remarkably similar out-of-order cores. The instruction set is a contract, not a design — which is why the same C code runs on both after nothing more than a recompile.

06 The supply chain

The memory hierarchy

A core can execute an instruction in a quarter of a nanosecond, but fetching data from RAM takes around 90 — roughly 400 clock cycles of waiting. The entire hierarchy of caches exists to hide that gap: small, fast copies of whatever you touched recently, stacked between the registers and RAM.

    Caches work because programs have locality: they reuse the same data (temporal) and march through neighboring data (spatial). Memory moves in 64-byte cache lines, so touching one array element drags its fifteen neighbors into cache with it — which is exactly why the tight loop above almost never misses.

    07 The assembly line

    Pipelines

    Fetch, decode, execute, access memory, write back — five stages, each built from different hardware. If the core ran one instruction start-to-finish before touching the next, four fifths of that hardware would idle at any moment. The fix is a factory’s: start the next instruction into stage one while the previous is in stage two.

    Instructions finished0

    Pipelining does not make any single instruction faster — it makes the stream faster, approaching one finished instruction per cycle. Real cores stretch these five stages into 14–20 finer ones to hit higher clock speeds. The catch: the longer the line, the more work is in flight on a guess — which is the next chapter.

    08 The gambler

    Branch prediction

    Roughly one instruction in five is a branch — an if, a loop test, a function return. The pipeline needs to fetch the next instruction now, but a branch’s outcome is not known until it executes, a dozen stages later. So the CPU gambles: a predictor guesses the outcome from past behavior and the core barrels ahead speculatively.

    Instructions retired0
    Cycles lost to flushes0
    Effective IPC—

    A misprediction throws away every younger instruction in the pipe — a ~15-cycle hole at modern depths. Predictors earn their silicon: the best hit 95–99% by tracking patterns and history, and dropping from 99% to 95% accuracy can cost real programs several percent of their speed. Speculation has a dark side, too: in 2018, Spectre and Meltdown showed that a CPU’s discarded guesses can leak secrets through the cache — a reminder that this machinery is anything but cosmetic.

    09 The dispatcher

    Superscalar & out-of-order

    A modern core is superscalar: it has multiple execution units and can start 4–8 instructions per cycle. But program order rarely cooperates — instruction 2 may need instruction 1’s result while instruction 3 needs nothing at all. So the core re-orders: any instruction whose inputs are ready may run, and a reorder buffer puts the results back in program order afterward.

    The machinery behind this — register renaming to erase false conflicts, a scheduler that watches operands become ready, and a reorder buffer (hundreds of entries deep on current cores) that retires results strictly in program order so the program never notices the shuffle. Exceptions and interrupts stay precise for the same reason: the visible state only ever advances in order.

    10 The team

    Multi-core & simultaneous multithreading

    Around 2005, clock speeds hit a power wall — so instead of one faster core, chips grew more cores. Today even phones carry eight. But adding cores only helps work that can be split, and almost every real program has a stubborn serial part. Try it: scale the chip and watch where the speedup stops.

    Speedup vs 1 core—

    That flattening curve is Amdahl’s law: if 10% of a program is serial, no number of cores can make it more than 10× faster. SMT (Intel’s brand name: Hyper-Threading) is different from adding cores — it gives one core two instruction streams so that when one stalls on memory, the other fills the idle execution slots. Two threads, one kitchen: typically +15–30% throughput, not +100%.

    Threads, processes, and who decides what runs

    A process is a running program with its own private memory; a thread is one instruction stream inside it. Your machine runs hundreds of threads on a handful of cores because the operating system context-switches: a hardware timer interrupt fires about a thousand times a second, the core saves one thread’s registers to memory, restores another’s, and resumes — in a few microseconds. Interrupts are also how keyboards, disks, and network cards get the CPU’s attention: the illusion of “everything at once” is scheduling, done fast.

    11 The sibling

    CPU vs GPU

    Everything in the last ten chapters was spent on one goal: make this instruction finish sooner. Caches, predictors, out-of-order machinery — all of it buys latency. There is a second way to spend the same transistors, and it is worth one chapter here because it shows where the CPU’s argument stops: give up the cleverness, and you can afford thousands of slow lanes instead of eight fast cores.     12 The numbers

    Reading a spec sheet

    CPU marketing is a wall of numbers, and the biggest one — gigahertz — is the most misleading. Real performance is a product: clock × IPC × cores that actually get used. Expand each metric for what it means, why it matters, and the misconception to avoid.

    Which chip is faster?

    Chip A

    4.8 GHz · IPC 1.6

     

    Chip B

    3.6 GHz · IPC 3.2

     

    What it is. How many times per second the pipeline advances — 5 GHz is five billion ticks, 200 picoseconds each.

    Why it matters. Every stage of every core moves once per tick, so throughput scales with it — when nothing stalls.

    Misconception. “More GHz = faster CPU.” A 3.6 GHz core retiring 3 instructions per cycle beats a 5 GHz core retiring 1. And RAM does not tick faster because your core does — higher clocks just wait more cycles per miss.

    What it is. Instructions actually retired per clock tick, averaged over a real program.

    Why it matters. It is the other half of performance: clock × IPC = instructions per second. Every chapter above — caches, predictors, out-of-order — exists to raise it.

    Misconception. IPC is not a fixed property of a chip. The same core might average 4 IPC on tight numeric code and 0.5 on pointer-chasing code. “15% more IPC” in marketing means “on our benchmark mix.”

    What it is. How many independent execution engines share the die.

    Why it matters. Parallel throughput: builds, renders, servers, and heavy multitasking scale with cores.

    Misconception. Twice the cores is not twice the speed — Amdahl’s law caps the gain at the serial fraction, and plenty of everyday software barely uses four.

    What it is. Hardware instruction streams. “8 cores / 16 threads” means each core juggles two streams via SMT.

    Why it matters. The second thread recycles stall bubbles — a cheap 15–30% throughput gain on mixed workloads.

    Misconception. 16 threads ≠ 16 cores. The two streams share one core’s execution units, caches, and bandwidth — they split a kitchen, not staff a second one.

    What it is. On-die SRAM — the L1/L2/L3 hierarchy from chapter 06.

    Why it matters. If your working set fits, misses collapse and IPC soars — it is why gaming chips with stacked extra L3 (96 MB+) win benchmarks at lower clocks.

    Misconception. Bigger is not automatically better: cache beyond your working set is silicon you paid for and never use, and larger arrays are slower to search.

    What it is. The opportunistic clock a core may reach briefly when power, current, and temperature allow — usually with only one core active.

    Why it matters. Snappy single-threaded moments — app launches, browsing — live in boost.

    Misconception. The box number is not a sustained all-core speed. Load every core and clocks settle far lower, set by cooling — boost is a sprint, not a pace.

    What it is. Thermal design power — the heat budget the cooler must dissipate under sustained load.

    Why it matters. Power is the modern constraint: the same silicon runs at 15 W in a thin laptop and 125 W in a tower, at very different sustained speeds.

    Misconception. TDP is not maximum draw — desktop chips routinely burst well above it for seconds at a time before power limits rein them in.

    What it is. How fast the memory controller can stream data from RAM — channels × transfer rate.

    Why it matters. Sixteen hungry cores share it; many-core chips and integrated GPUs starve without enough.

    Misconception. Bandwidth does not fix latency. Streaming a movie fast is not the same as answering a single question quickly — a pointer chase stalls just as long on a wide bus.

    What it is. Work done per joule — the ratio that now drives CPU design more than raw speed.

    Why it matters. Phones, laptops, and datacenters are all thermally limited; under a fixed power cap, the most efficient design is the fastest one.

    Misconception. Efficiency is not code for slow. Apple’s M-series topped laptop benchmarks precisely because it did the most per watt.

    13 The lineage

    Eighty years of CPUs

    1985

    Intel 386 — 32 bits

    32-bit registers and protected memory make real multitasking operating systems possible. The PC grows up.

    275,000 transistors

    1993

    Pentium — superscalar

    Two pipelines side by side: more than one instruction per cycle for the first time in the mainstream. The IPC race begins.

    3.1M transistors

    2000

    Pentium 4 — the GHz wall

    A pipeline stretched to 31 stages chases raw clock speed — and slams into the power wall. The industry’s most instructive failure.

    42M transistors

    2003

    Athlon 64 — x86-64

    AMD extends x86 to 64 bits so cleanly, while keeping old software running, that Intel adopts AMD’s design. Memory ceilings vanish.

    106M transistors

    2005

    Dual core

    Clocks stall, so cores multiply. The free lunch ends: from now on, software has to go parallel to go faster.

    2 cores, 1 die

    2017

    AMD Zen — and chiplets

    A 52% IPC leap revives competition; two years later, chiplets replace one giant die with small, cheap, stackable ones.

    4.8B transistors

    2020

    Apple M1 — ARM arrives

    An ARM chip outruns x86 laptops at a fraction of the power: 8-wide decode, a huge reorder buffer, unified memory. Efficiency becomes the headline.

    16B transistors

    2021

    Hybrid cores

    Performance cores for sprints, efficiency cores for background hum — phones proved it, desktops adopted it, and the OS scheduler became part of the CPU design.

    P + E cores

    2024

    The AI PC

    Neural accelerators join the die next to CPU and GPU. The modern processor is a team of specialists — and the CPU is the coach.
