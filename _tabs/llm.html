Large Language Models

The missing chapter between machine learning and ChatGPT — how a trained neural network becomes a system that generates coherent language, one token at a time.

How can a computer generate the next word in a sentence?

That one question is the whole subject. Every chapter on this page is a piece of its answer — and every paragraph an LLM has ever produced is that answer, repeated thousands of times.

01 The original goal

What is a language model?

Strip away everything else and a language model does exactly one job: given the text so far, assign a probability to every possible next token. Not “understand the sentence,” not “answer the question” — just predict what comes next. Everything an LLM appears to do emerges from doing that one job extremely well, over and over.

Watch the prediction happen

Type a few words (or pick a prompt) and watch a real language model rank what should come next. This one is deliberately transparent: it is an n-gram model — real counted statistics over the tiny 45-sentence corpus shown below — so you can audit every probability. A production LLM computes the same kind of distribution with a transformer instead; chapters 3–7 build that machine.

Keep clicking append. That loop — predict a distribution, pick one token, feed it back in, predict again — is autoregressive generation, and it is the entire mechanism behind every paragraph ChatGPT has ever written. There is no second mechanism.

Why would prediction produce intelligence-shaped behavior?

Because predicting the next token well quietly requires almost everything else. To continue “the capital of France is” you need geography; to continue “she handed the scalpel to the” you need to track who is in the room; to continue a half-finished Python function you need syntax and intent. A model pushed hard enough on next-token prediction is forced to compress real structure about language and the world into its parameters. That is the bet behind the entire field — and it paid off in a way few predicted.

Our little counting model above can only memorize short patterns from 45 sentences. The rest of this page is about the architecture that made prediction scale: the transformer.

02 The unit of language

Tokens: what the model actually reads

A model never sees words or letters — it sees tokens: chunks of text drawn from a fixed vocabulary, each identified by a number. Common words become single tokens; rare words get split into reusable pieces.

A real tokenizer, trained in your browser

This is genuine byte-pair encoding (BPE) — the same algorithm family behind GPT-style tokenizers — trained live on the exhibit’s corpus when this page loaded. It started from single characters and repeatedly merged the most frequent adjacent pair. Type anything; the ▁ mark means “this token starts a new word.”

Why tokens, and not characters or dictionary words?

Characters make sequences brutally long — every extra position costs attention computation (chapter 5 shows why that cost grows quadratically). Whole dictionary words can’t handle “transformerify”, typos, code, or Finnish. Subword tokens are the engineering compromise: frequent strings get their own token, everything else decomposes into pieces, and no input is ever truly out of vocabulary. You saw it above — this tokenizer has never seen “catastrophe”, yet it still encodes it from pieces like ▁cat it learned elsewhere.

Two consequences worth remembering: models are billed and limited in tokens (a “128K context” means 128K tokens, not words), and anything the tokenizer chops awkwardly — unusual names, arithmetic digits, other alphabets — starts at a disadvantage before the model even begins.

03 From symbols to geometry

Embeddings: every token becomes a vector

Token ID 57 means nothing to a neural network — you can’t do calculus on a dictionary index. So the first layer of every LLM is a giant lookup table that turns each token into a vector: a list of numbers the network can add, compare, and transform. The magic is that after training, distance in that space means similarity in usage.

A real embedding space, learned from the corpus

Nothing here is hand-placed. When the page loaded, every word’s co-occurrence statistics were computed from the corpus, weighted by pointwise mutual information, and projected to 2D with a real spectral method (power iteration). Words used in similar contexts genuinely drift together — cat lands near dog because the corpus uses them alike, not because anyone told it they are both pets. Click a word to see its nearest neighbors in the full space; click a second word to compare the pair; drag a word to measure distances from anywhere.

Inspector

Click any word on the map.

Neighbor similarity is cosine similarity in the full 92-dimensional space; the 2D picture is a projection and slightly distorts distances — exactly the caveat that applies to every published embedding visualization.

Production models do this with learned embeddings — the lookup table is trained by gradient descent along with everything else (the loop you built on the machine learning exhibit), and each token gets thousands of dimensions rather than two. But the principle is identical to what you just touched: embeddings encode learned relationships between usages, not dictionary definitions. “Bank” sits near both “river” and “loan” because text uses it both ways — ambiguity the next chapters resolve using context.

04 Order matters

Positional encoding: telling the model where words are

Attention (next chapter) looks at all tokens at once, with no built-in notion of order. Without help, “the cat chased the dog” and “the dog chased the cat” contain exactly the same set of vectors — the model literally could not tell who chased whom. The fix: add a position signature to every token’s embedding.

Prove it to yourself

Below, both sentences are embedded with the real educational model from the next chapters. With positional encoding off, the two sentences’ token vectors are the same multiset — the check runs live on the actual numbers. Toggle it on and watch each position’s sinusoidal signature split them apart.

The position signatures themselves

Each row is one position, each column one embedding dimension; color is the sinusoidal value that gets added to whatever token sits there. Every row is unique, nearby rows are similar — which is exactly what lets the model judge both order and distance. Click a row to see its raw numbers.

This exhibit uses the original sinusoidal recipe from the 2017 transformer paper because every value is a formula you can check. Modern models mostly use variants learned during training or rotary embeddings — different mathematics, same job: make position part of the vector, so that everything downstream can care about word order without any component ever processing tokens one-by-one in sequence.

05 The signature mechanism

Self-attention: every token looks at every other token

This is the idea the whole architecture is named for. Each token asks a question (its query), every token advertises what it holds (its key), and the match between them decides how much of each token’s value flows into the new representation. Three small matrix multiplications, a scale, a softmax — that is the entire trick.

The real computation, end to end

Everything below is genuine attention mathematics running in your browser on intentionally tiny matrices (8-dimensional embeddings, one 4-dimensional head) so every intermediate value fits on screen. The weights are seeded random — untrained, and labeled so — because the point here is the machinery. Click any token to make it the query.

Why this mechanism won

Older sequence models passed information along word by word, so distant words faded. Attention gives every token a direct connection to every other token — “it” can reach back to “the cat” in one hop, whether that is 3 or 3,000 tokens away. And because each row’s computation is independent, the whole thing is one big matrix multiplication — precisely the shape of work GPUs devour. The cost: every-token-to-every-token is n² pairs, which is why context length is expensive (chapter 8).

Notice the causal mask in the demo: for generation, a token may only attend to what came before it. During training this lets one sentence teach the model at every position simultaneously — each token predicts its successor using only its past.

06 Many relationships at once

Multi-head attention

One attention pattern can only encode one kind of relationship at a time. So transformers run several attention heads in parallel — each with its own Q, K, V projections, each free to specialize — then concatenate the results. One head may track grammar, another nearby words, another a pronoun’s far-away referent.

Four heads, four patterns

Each grid shows one head’s full attention matrix for the sentence — row = the token doing the looking, column = the token being looked at, brightness = weight.

Real (untrained): these four heatmaps are genuinely computed by four attention heads with seeded random weights — the real mathematics, before training has given the heads any roles. Switch modes to see the kind of division of labor training tends to produce.

The second mode is an illustrative sketch, not a rendering of any production model — but the phenomenon is real: researchers routinely find trained heads that track syntax, previous occurrences of the current word, or which earlier name a pronoun refers to. The deeper lesson is architectural: nobody assigns these roles. Training pressure alone pushes heads to divide the labor, the same way gradient descent shapes every other parameter.

07 The repeating unit

Transformer blocks: the assembly line

Attention alone is not a network. It lives inside a block: normalize → attend → add the result back to the input (a residual connection) → normalize → feed-forward network → add back again. Stack that block dozens of times and you have a GPT. The residual “add back” is why very deep stacks stay trainable: each block only has to learn a refinement, never rebuild the signal from scratch.

Two roles, cleanly split: attention moves information between positions; the feed-forward network processes each position on its own (and holds roughly two thirds of the parameters — much of the model’s factual knowledge is believed to live there). Layer normalization keeps activations in a healthy range so 96-layer stacks train without exploding — the same numerical-stability engineering you saw matter for gradient descent.

08 The model's working memory

Context windows: what the model can see

A transformer predicts from a fixed-size window of recent tokens — its context. Anything outside the window does not exist for the model. Not “vaguely remembered” — gone, unless it is re-sent with the next request.

Watch a conversation outgrow its window

A simulated chat grows message by message (token counts are illustrative). Pick a window size and watch which turns remain visible to the model when it writes its next reply.

Tokens in conversation — Visible to the model — Fallen out of context —

Why not make the window infinite? Chapter 5’s mathematics: attention compares every token with every other token, so doubling the window roughly quadruples attention compute and grows the key/value cache that must sit in GPU and high-bandwidth memory during generation. Long context is a genuine engineering trade-off — compute, memory, and cost against recall — for every provider, which is why “the assistant forgot the start of our chat” is an architecture fact, not a bug.

09 Two different lives

Training vs. inference

Every model lives twice. Training happens once, on cloud-scale GPU clusters over weeks: predict, measure the miss, push every weight slightly downhill, repeat trillions of times. Inference happens every time you chat: the same forward pass — but nothing is learned. The weights are frozen.

Inference — every time you chat

Forward pass ↓ Distribution over next tokens ↓ Sample one token ↓ Append & repeat ✕ no loss, no learning

This side is real: the corpus-trained model from chapter 1, generating token by token through the sampling pipeline from chapter 10.

This split answers a common confusion: ChatGPT does not learn from your conversation. During a chat it only runs forward passes; your messages shape the context window, never the weights. When an assistant seems to “remember,” that is engineering around the model — conversation history or notes re-sent inside the context — not the network changing. Weights change only when the provider trains a new model version at the factory. The capstone shows where fine-tuning and human feedback fit into that factory pipeline.

10 Choosing the next token

Sampling: temperature, top-k, top-p

The model hands you a probability distribution — it never picks the token. Decoding does, and three dials control it: temperature reshapes the distribution, top-k keeps only the k most likely candidates, top-p keeps the smallest set whose probabilities add up to p. Same model, wildly different text.

Rules of thumb that fall straight out of the mathematics: temperature → 0 approaches greedy decoding (always the argmax — deterministic, repetitive); high temperature flattens the distribution toward noise; top-p adapts to confidence (a sure distribution keeps few candidates, an uncertain one keeps many), which is why it usually beats a fixed top-k.

11 Fluent ≠ true

Hallucinations: why fluent output can be false

Everything on this page so far generates statistically likely continuations. Nothing anywhere checks whether a continuation is true — by default there is no lookup step, no database, no fact-checker in the loop. When likely and true coincide (they usually do — the training text was mostly written by people describing reality), the model looks knowledgeable. When they diverge, it produces confident fiction.

Manufacture a hallucination

Our corpus contains “the cheese was made of milk”, “the bread was made of wheat”, and “the house was made of stone” — and says nothing about what the moon is made of. Ask anyway. The model does what every language model does: continues with what usually follows “made of”, with real confidence numbers attached.

Note what did not happen: the model did not lie, and it did not malfunction. It answered the only question it is built to answer — “what text is likely here?” — flawlessly. The mismatch is between that question and the one you actually asked.

Scale changes the odds, not the mechanism: a frontier model’s “corpus” covered so much ground that likely continuations are usually correct — which makes the failures more dangerous, because fluency reads as authority. The pattern to watch for is unsupported specificity: exact citations, dates, statistics, or API names in areas where the training data was thin. Probability of the form is high; evidence for the content may be nonexistent.

Mitigations exist at the system level — retrieval that pastes real documents into the context window (chapter 13), tool calls that check sources, models trained to express uncertainty and decline — and modern assistants hallucinate far less than raw base models. But none of it changes the default: a language model’s output is a claim about language, and treating it as a claim about the world is a decision that deserves verification when it matters.

12 Why “large”

Scaling: from our toy to the frontier

Everything you have inspected on this page — the same mathematics, the same blocks — becomes a frontier model chiefly by scaling up: more dimensions, more heads, more layers, more data, more compute. The discovery that made the industry: prediction quality improves smoothly and predictably as all three grow together.

Slide from millions to a trillion parameters

The readouts are computed live from the parameter count using standard engineering rules of thumb (2 bytes per weight at fp16; ≈20 training tokens per parameter, the “Chinchilla” heuristic; ≈6 × parameters × tokens floating-point operations for training) — conceptual estimates for intuition, not any specific model’s specs.

Past a few billion parameters, one computer stops being enough: weights shard across GPU fleets, training runs on distributed clusters where schedulers and interconnects matter as much as math, checkpoints stream to storage in terabytes, and serving a single reply becomes a networked systems problem. Scale is why LLMs are as much an infrastructure story as an algorithms story — and energy use scales with the compute, which is why efficiency research is now a first-class concern.

13 The model becomes a system

Beyond the transformer

A bare model predicts tokens. Products wrap it in systems. Four ideas you will meet everywhere — presented here as conceptual overviews (none of them is an intrinsic part of every LLM, and none is implemented live on this page).

Retrieval-Augmented Generation (RAG)

Before the model answers, a search system fetches relevant documents and pastes them into the context window. The model still only predicts tokens — but now the likely continuation is grounded in text that was retrieved seconds ago, which slashes hallucinations about private or recent information. It is engineering around chapter 8, not a change to the model.

Mixture of Experts (MoE)

Replace each block’s one feed-forward network with many “experts” and a tiny router that sends each token to just a few of them. Result: a model with enormous total parameters where any single token only pays for a fraction of the compute. Several frontier models are built this way.

Tool use

Let the model emit special tokens that mean “call the calculator / search / run this code,” execute the call outside the model, and feed the result back into the context. The model contributes judgment about when and what to call; the tool contributes correctness the weights cannot guarantee.

Agents

Put tool use in a loop: plan, act, observe the result, decide the next step — dozens of forward passes stitched into one task. Every “AI agent” you meet is still chapter 1’s next-token loop underneath, orchestrated by ordinary software.

The question, answered

So — how can a computer generate the next word?

You can assemble the whole answer yourself now. Split the text into tokens from a fixed vocabulary. Look each one up in an embedding table so it becomes a vector, and add a positional signature so order survives. Pass the stack through dozens of transformer blocks, where self-attention lets every token pull in exactly the context it needs and feed-forward layers refine each one — all of it just matrix multiplication, trained once by gradient descent and frozen. Read off a probability for every token in the vocabulary, let temperature, top-k, and top-p pick one, append it, and go again. Repeat a few hundred times and you have a paragraph — fluent by construction, true only insofar as likelihood and truth happen to agree.

And now the How ChatGPT Works capstone stops being magic: it is this page’s machinery — deployed behind a chat interface, tuned with human feedback, running on GPU fleets in the cloud, streaming tokens back to you across the internet. You have already learned every concept it assembles. Go watch them work together.
