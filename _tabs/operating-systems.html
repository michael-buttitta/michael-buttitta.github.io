Here is the whole page in one sentence: between the applications you see and the silicon you own sits one program — the operating system — that decides which code runs next, which memory belongs to whom, where every file physically lives, and whether any given request should be allowed at all. Windows, macOS, Linux, Android, and iOS are all answers to the same question. Every chapter below shows one part of the job, and at the end you get to run the whole machine yourself.

01 The fundamental question

What is an operating system?

A computer is a pile of parts — CPU, memory, storage, GPU, network card — each of which does exactly what it is told and nothing more. Applications, meanwhile, all want those parts at the same time. Something has to sit in the middle. Toggle the world below between no operating system and with an operating system and watch what changes.

Without a coordinator, three programs writing to the same memory or disk at once corrupt each other — the flashes are collisions. With one, every request is checked, queued, and dispatched in order. Early personal computers really did work the first way: one program owned the whole machine, and a bug in it froze everything.

That is the definition worth keeping: an operating system is the program that manages all other programs and all of the hardware. It multiplexes the CPU so dozens of applications appear to run at once, hands out memory so they cannot trample each other, turns “save this file” into disk blocks, and polices who may do what. The rest of this page is simply that job description, one responsibility at a time.

03 The core of the core

The kernel

Strip away the desktop, the icons, and the bundled apps, and what remains is the kernel: the one program with full authority over the hardware. Everything you see runs above it, in user space; the machine itself sits below it. Click any subsystem to see what it does, then send a request across the boundary.

Why the two-floor building? Modern CPUs have privilege levels baked into the silicon: kernel code runs in a mode that may touch any memory and any device register; application code runs in a restricted mode where those instructions simply fault. The only doorway between the floors is the controlled system call. That single architectural choice is why a crashing game takes down the game — not the machine — and it leans directly on hardware features covered in Inside a Modern CPU.

04 Programs in motion

Processes & threads

A program on disk is a recipe; a process is that recipe being cooked — code plus its own private memory, open files, and at least one thread of execution. Launch some applications, then expand one to see the threads working inside it.

Each process gets an ID and its own isolated address space — the browser cannot read the game’s memory, which is why one crash stays contained. Threads inside a process are lighter: they share that memory, so the game’s physics thread and render thread can hand data to each other instantly — and can also run on different CPU cores at literally the same time.

05 Who runs next?

CPU scheduling

One CPU core executes one thread at a time, yet your machine juggles hundreds. The scheduler decides who runs next and for how long — and that policy shapes how fast the computer feels. Run the same five processes under three classic policies and compare the results.

Results for this run

Watch the mouse-click process: under First Come, First Served it waits behind the long video encode; under Round Robin it gets a turn almost immediately. That is the classic trade — FCFS is simple and fair by arrival, Round Robin buys responsiveness with extra switching, and Priority serves the important first but can starve the unimportant. Real schedulers (Linux’s EEVDF, Windows’ multilevel feedback queues) blend all three ideas.

06 The illusion of simultaneity

Context switching

Multitasking on one core is a magic trick: the CPU runs one thread, freezes it mid-thought, runs another, and switches back before you notice. The frozen “thought” — register values, program counter, stack pointer — is saved into the process’s control block and restored later, byte for byte.

Push the slider right and the two apps blur into “simultaneous” — but the orange slivers of switching overhead eat a growing share of the core. A real switch costs on the order of microseconds (plus cache warm-up afterwards), and a busy machine does thousands per second: cheap enough to feel free, never actually free. Multiple cores help — but each core still runs exactly one thread at any instant.

07 Handing out RAM

Memory management

Every process wants memory, and none of them may touch anyone else’s. The OS keeps the ledger: which pages of RAM are free, which belong to whom, and which are shared. Launch and quit applications below, then try the attack.

Notice two things. Freed pages leave holes, and new allocations happily fill scattered holes — a taste of why the OS allocates in fixed-size pages rather than one big slab. And the striped pages are shared: one copy of a common library mapped read-only into several processes at once. The rogue write is refused in hardware — that’s a segmentation fault, the wall that makes process isolation real.

08 The grand illusion

Virtual memory

Here is the twist: processes never see real RAM addresses at all. Each one lives in its own virtual address space — a private, seemingly contiguous stretch of memory starting at zero — and a page table maps every virtual page to wherever it actually is: some frame of physical RAM, or parked on disk. Touch a page and follow the translation.

    Both processes happily use “page 0” — and land in different physical frames. Pages marked on disk were swapped out to make room; touching one raises a page fault, the OS reads it back in (evicting someone else), and the program never knows it happened — except in lost microseconds. This is also why “using more RAM than you have” works, just slowly. The full memory hierarchy story lives in Inside Computer Memory.

    09 Where your stuff actually lives

    File systems

    A drive doesn’t know what a “file” is — it stores numbered blocks of bytes. The file system is the OS’s scheme for turning those blocks into names, folders, sizes, owners, and timestamps. Explore the tree, then cut the power mid-write and see why journaling exists.

      Select a file to see its metadata and where its blocks sit on disk.

      The metadata panel is the point: the file system stores far more than contents. Permissions gate access (chapter 12), and the journal is a write-ahead diary — the intent is recorded before blocks change, so after a crash the OS replays or discards the entry instead of leaving the disk half-updated.

      10 Speaking every dialect

      Device drivers

      Thousands of keyboards, printers, GPUs, and Wi-Fi chips exist, each with its own registers and quirks — and your applications know none of it. A driver is the translator: the OS defines one standard interface per device class, and each driver maps it onto one specific piece of hardware. Pick a device and follow a request down the stack.

      Application ↓ Operating systemgeneric input API ↓ DriverUSB HID keyboard driver ↓ Hardwarekey matrix scan

      The keyboard also shows the reverse direction: hardware raises an interrupt — a hardware signal that makes the CPU pause what it’s doing and run the driver’s handler — which is how a keypress gets noticed within microseconds without the OS constantly polling. Because the interface stays fixed, one OS supports thousands of devices by swapping drivers, and a new GPU needs a new driver, not a new Windows. The GPU driver’s remarkable job gets its own chapter in Inside a Modern GPU.

      11 The doorway to the kernel

      System calls

      User programs cannot touch disks, screens, or network cards directly — the CPU’s restricted mode forbids it. Instead they ask: a system call is a controlled jump into the kernel, which validates the request, does the privileged work, and returns a result. Pick a request and watch it cross the boundary.

      Applicationuser mode System callmode switch Kernelkernel mode Storagehardware Resultback to user mode

        Every “open,” every packet sent, every process spawned takes this trip — a busy program makes thousands of system calls per second. The kernel checks permissions on the way in, which is exactly where the rules from chapter 12 get enforced. The connection request continues into the kernel’s network stack, whose onward journey is the whole of How the Internet Works.

        12 The bouncer at every door

        Security & permissions

        Because every request funnels through the kernel, the kernel is the natural place to ask: should this be allowed? Accounts, permissions, and sandboxes are all answers. Try the same actions as three different users and read the verdicts.

          Layers, not one wall: accounts separate people, file permissions say who may read or change what, administrator elevation makes dangerous actions deliberate, and sandboxes shrink what an app can even ask for — a sandboxed app requesting the camera triggers that familiar permission prompt. Beneath it all, Secure Boot verifies each boot stage’s signature before running it, and code signing extends the same idea to apps and drivers. The signature math — and how the OS guards stored keys and encrypted disks — is the subject of Understanding Cryptography.

          13 The family portrait

          Modern operating systems

          Every chapter so far applies to all of them: same concepts, different engineering choices and priorities. Pick one — there’s no “best,” only best-for-what.

          Two threads run through the whole family. Android runs on the Linux kernel, and iOS shares its XNU core with macOS — kernel families outlive the products built on them. And all five draw the same line between kernel space and user space, schedule with priorities, page memory, and gate everything through system calls. Learn the concepts once and every OS becomes familiar. The same is true one level up: every cloud server, virtual machine, and container in Understanding the Cloud is one of these operating systems doing everything on this page.

          14 Setting the record straight

          Common misconceptions

          Seven things people believe about operating systems that aren’t quite true — each one a quick expand.

          The operating system is the desktop.

          The desktop, taskbar, and windows are one replaceable program among many — a shell running in user space. The OS is mostly the invisible machinery underneath: kernel, scheduler, memory manager, file systems, drivers. Linux makes this vivid by letting you swap desktops entirely, or run with none, on the same OS — and every server does exactly that.

          More RAM always makes a computer faster.

          More RAM helps until your working set fits — then extra gigabytes mostly sit as file cache. If a machine is slow because it’s constantly swapping to disk, RAM is a cure; if it’s slow because of a saturated CPU, a slow disk, or a misbehaving program, more RAM changes little. The bottleneck decides, and the bottleneck moves.

          Closing an app immediately frees all its memory.

          The OS does reclaim the process’s private pages when it exits — but apps often don’t fully exit (background helpers, tray processes), shared libraries stay resident for their other users, and caches are kept deliberately because free RAM doing nothing is wasted RAM. A “memory used” number staying high after closing an app is usually the OS being smart, not leaky.

          The CPU runs every application simultaneously.

          Each CPU core runs exactly one thread at any instant. With eight cores, eight threads truly run at once; the other hundreds are paused, waiting their turn. Fast context switching — thousands per second — creates the illusion of everything running together. It is time-sharing, performed so quickly you can’t perceive the gaps.

          Drivers are applications.

          Drivers are privileged kernel-side components, not programs you run from a menu. Most load automatically when hardware appears and have no window or icon. The distinction matters: a buggy application crashes itself, while a buggy driver runs with kernel privileges and can crash the whole machine — which is why a bad graphics or storage driver can blue-screen a PC and why modern OSes push drivers through signing and testing programs.

          Restarting always fixes the underlying problem.

          A restart throws away all accumulated state — leaked memory, wedged processes, stuck locks — and rebuilds the world from disk. That genuinely clears many symptoms, which is why it works so often. But the bug that produced the bad state is still there; if the same leak or race happens again, so will the problem. Restarting is a reset, not a repair.

          Linux is only for programmers.

          You have probably used Linux today without noticing: Android is built on the Linux kernel, and so are most web servers, smart TVs, routers, and cloud machines. Desktop distributions like Ubuntu and Mint install with a point-and-click interface comparable to Windows or macOS. The programmer-only reputation is decades out of date — Linux is simply most often used where nobody sees it.
